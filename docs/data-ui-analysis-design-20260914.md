## 1. 目的・対象・進め方

情報の確認漏れを管理し、既存画面で判断から議席仮定まで操作できることを確かめ、接戦の理由を説明する材料を充実させる。今回の対象は①未確認5情報源、②iPad・iPhoneを中心とする表示と操作、③既存8論点と接戦6選挙の分析である。

| 工程 | 作業単位 | 成果物 | 次へ進む条件 |
| --- | --- | --- | --- |
| A：情報更新 | 5情報源を一巡して再照合 | 情報源別結果、必要なデータ訂正、実行記録 | 確認できた範囲と未確認を明示。取得不能だけを理由にB・Cを止めない |
| B：画面・操作 | 基準画面を検証し、不具合を修正 | 検証記録、問題箇所の修正、必要な画面証拠 | 主要操作を妨げる不具合を解消。実機未確認は別記 |
| C：分析拡充 | 8論点を点検し、3回に分けて追加 | 論点別本文・州事例・根拠・確認条件 | 各回の公開可能部分を独立して検証・公開する |

原則A→B→Cの順で担当が進める。既存の日次観測は継続するため、作業開始時と反映前にmainを取り直す。同じデータを変更していた場合は最新更新を取り込む。全作業を一度にまとめて長時間の公開待ちにしない。

新しい勝率・因果係数・世論調査平均、全州への一律の詳説拡大、大規模な画面再設計、新しいバックエンドは今回の範囲に含めない。候補者の選択、未配分、保存・比較・共有、権限からの経路提示は既存機能を維持する。

### 3.2 調査方法と終了条件

1. 最新の実行記録・台帳・関連する名簿と評価を読む。既に解消した項目を再度「未確認」に戻さない。
2. 公開検索で当該発行者の正式なページ・PDF・候補者一覧を特定し、原文を開いて対象・日付・根拠箇所を照合する。
3. 登録先が移転していた場合は同じ発行者の移転先を確認する。同じ主張を確認できる別資料は別sourceIdに登録し、どの資料で何を確認したかを残す。
4. 同一URLへの同条件の失敗を繰り返さない。一巡につき登録先の確認と、発行者内の別ページ・正式資料の探索を行い、解決しなければ理由・試した先・次の確認方法を記録して次の項目へ進む。アクセス制限の回避は行わない。
5. 検索抜粋、別機関の評価、陣営の自己紹介を、それぞれ正式名簿や当該評価機関の原文の確認成功へ置き換えない。

Alaska Public Mediaの個別記事を確認できても、政治一覧の全更新を確認したことにはしない。Sabatoが確認できない間は最後に照合した評価とその確認日を維持し、Inside Electionsだけの更新を「2機関の最新評価を再確認」と表示しない。評価が変わった場合だけ、既存の集計方式で地図・初期値を更新し、保存済み基準は維持する。

### 3.3 状態・データ・記録

既存の [ObservationSource / ObservationRun](../src/data/observation-model.ts) を使う。source.checkStatusはchecked／unavailable／not-checkedの3値であり、未定義のreviewingをsourceへ追加しない。取得済み・内容未照合はnot-checkedと実行記録の理由で表し、run全体のreviewingと区別する。

記録する項目はsourceId、試したURL、対象期間、確認時刻、結果、照合箇所、未確認理由、次回の確認方法。既存runファイルのsourceResultsを利用し、巨大な取得本文や認証情報は保存しない。取得失敗が実行記録にあるのに台帳がnot-checkedのままの場合は、実際の結果に合わせて整合させる。lastSuccessAtとcontentVerifiedAtは内容を照合した資料だけ更新する。

同一の正式資料のURL移転は履歴をrunへ記録して台帳を更新する。異なる資料を使った確認では元の取得不能状態を成功に変えず、新資料と根拠を明示する。候補者が増減しても表示名によるIDの再発行はせず、既存candidateIdと過去の調査参照を保持する。

**Aの完了判定：** 5件すべてに今回の結論と根拠があり、確認できた変更を反映したら「一巡完了」。未確認が残る場合は「照合完了」とは呼ばず、partialのままB・Cへ進む。未確認の継続追跡は既存の日次観測が担う。

## 5. C：8論点と接戦州の分析拡充

### 5.1 追加する説明

各論点の本文は次の流れで構成する。順序は共通にし、同じ一般論を8回繰り返さない。

1. **何が争点か：** 現在の政策・出来事と、争われている選択肢。
2. **どこ・誰に関係するか：** 家計・産業・地域への影響と、確認できた対象範囲。
3. **候補者の違い：** 両主要候補の政策・採決・実績を同じ軸で比較。
4. **投票との関係：** 有権者の評価を直接確認できる証拠と、まだ分からない部分。
5. **議席と次の確認：** 議会権限との接続、結果を分ける条件、次に確かめる調査・指標。

政策による経済的影響、有権者の問題意識、候補者評価、支持先、投票参加はそれぞれ別の段階である。因果を示す証拠がなければ「影響しうる」「検証する条件」として記述し、支持率の差だけから原因を断定しない。

### 5.2 8論点の調査対象と順序

下表の州は調査候補であり、投票への影響が確認済みという意味ではない。原文で裏付けられない組合せは無理に事例化せず、理由を記録する。

| 公開回 | 論点ID・名称 | 優先して確かめる内容・州 |
| --- | --- | --- |
| C1 | household-economy：家計・税・財政 | OH・TX・NH：生活費・税負担への訴え、対象層、政策の効果と候補者評価の区別 |
| C1 | trade-industry：貿易・産業・農業 | MI：製造業・関税・雇用と候補者の違い。IAの既存農業事例は補助事例として保持 |
| C1 | health-family：医療・家族・教育 | ME・MI・OH：医療費・保険・地方医療、採決や提案と有権者の評価 |
| C2 | immigration：移民・国境 | TX中心：国境執行、合法移民、生活・労働への影響と争点の優先順位 |
| C2 | energy-climate：エネルギー・気候・環境 | AK中心：資源開発、電力・燃料費、地元利益と環境負担。開発支持と候補支持を分ける |
| C2 | rights-institutions：法の支配・権利・選挙制度 | ME・NH・MI：政権との距離、個別採決、制度・権利への立場。批判と本人の反論を併記 |
| C3 | security-foreign：外交・安全保障 | MI・AKを候補に、外交・軍事・対外政策が州内の関心や候補者差となっている原文を探す。直接の根拠がなければ全国の制度説明と未確認範囲を示す |

全8論点を対象にするが、8論点×6州の48枠を機械的に埋めない。各論点で最も説明力のある1〜2事例を優先し、州間の違いを確認できる場合に比較を加える。1州の証拠しかなければ全国へ一般化しない。

### 5.3 表示量と掲載場所

| 掲載場所 | 目安と役割 |
| --- | --- |
| 全国情勢・注目州の入口 | 現行の短い要約を維持。重要材料は最大2件 |
| 論点のsummary | 2〜3文、120〜200字程度で中心的な対立を示す |
| 論点本文 | 4〜5節、各150〜250字程度。本文全体は概ね800〜1,200字。根拠と反証に必要なら調整 |
| 州事例 | 1〜2件を優先し、各250〜400字程度。候補者差・投票との関係・確認条件を含める |
| 出典と限界 | 主張に根拠を対応付け、重要な限界は本文近く、資料の細目は既存の出典表示へ |

文字数は品質判定の機械的な条件ではない。既存の「8つの論点」パネル、州詳細、ニュースの導線を再利用し、全国情勢の入口へ長文を追加しない。事例全文を州詳細とニュースへ重複掲載せず、要約と関連付けを使う。

利用者への更新報告では、州・選挙・候補者の背景→直前の出来事→誰のどの発言への応答か→今回の変化→判断への意味と限界の順に説明する。サイトの短い要約をそのまま送るだけにせず、報告だけで経緯を人に説明できる文脈を付ける。過去の発言からの推論は推論と明示する。

### 5.4 データへの対応

[IssueReport](../src/data/research-model.ts)の既存フィールドを基本にする。

- summary：中心となる対立、readingGuide：読む順序。
- sections：上記の説明節。各ResearchSectionにevidenceKind・evidenceIdsを持たせる。
- caseStudies：州・選挙の事例。stateFips・electionIds・sourceIds・evidenceIdsを維持。
- 既存の研究用SourceとEvidenceRefのレジストリへ新資料を追加し、source→evidence→本文を追跡できるようにする。
- research.tsの一律生成部分へ論点別の本文を適用する。必要ならデータ専用の `src/data/issue-report-content.ts` に分け、UIやresearch.tsを逆参照しない。
- 観測データの根拠を研究本文へ再利用する場合、既存の研究側レジストリで解決できるよう明示的に接続する。別レジストリのIDをそのまま置いて参照切れを作らない。同一資料の矛盾した二重登録を避ける。
- RaceBrief・CandidateBriefと観測用comparisonの同じ主張が異なる場合は、原文で日付を確認して関連表示を整合させる。古い調査・採決の履歴は新しい発言で消さない。
- 新しいstateId・electionId・candidateId・issueIdは必要な場合以外作らない。変更した本文だけupdatedAtを進める。

### 5.5 調査の合格条件

重要な主張ごとに、発行者・公開日・対象期間・根拠箇所を持つ。候補者公式資料は本人の立場の証拠として扱い、実績の効果や有権者の支持は別資料で確認する。反応・批判を扱う場合は前後の文脈と重要な反論も確認する。調査原表、統計の公表主体、議会記録などを優先し、ニュースは出来事の経緯を補う。

当該論点の主要な対立、対象地域・層、候補者差、制度との接続、投票効果の不確実性、次の確認条件が根拠付きで説明できた場合にsubstantialへ変更する。文字数や事例数だけで変更しない。証拠が足りない場合はpartialのまま、執筆できた部分と未解決の問いを残す。存在しない根拠を補って全件substantialにすることは完了条件ではない。

main反映前に競合を確認し、通常のfast-forwardで反映する。各工程の変更を独立したコミットまたは小さなコミット群にし、データ更新と広い表示変更を混在させない。公開は既存のPages workflowで行い、対象SHA・実行結果・公開内容を照合する。失敗時は既存の正常な公開を維持し、共有ブランチの履歴を書き換えない。

## 7. 完了報告と未解決の管理

各工程について「実施したこと／確認した根拠／公開結果／残っていること」を短く報告し、CURRENT_STATE.mdに証拠の参照先を残す。

- A：5件の確認結果を一覧にし、未確認件数と理由を明記する。
- B：B1〜B8の結果と確認環境を記録し、模擬画面・実機・未検証を区別する。
- C：8論点それぞれについて追加内容、partial／substantial、未解決の問いを記録する。3回の公開が終われば対象8論点の点検・拡充を一巡完了とする。
- 取得不能、証拠不足、環境上の未検証が残れば「全件確認済み」と報告しない。
- 文書作成は本設計の保存をもって完了とし、実作業の進捗とは分ける。次工程はAの一巡から開始する。
